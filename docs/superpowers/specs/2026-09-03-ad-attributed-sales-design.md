# 「売上/日」に広告経由の売上個数を並べる

2026-09-03

## 目的

「売上/日」は各行が ASIN、各列が日付で、セルにその日の売上個数が入っている。
ここに **広告経由で売れた個数** を並べ、全体の売れ行きのうちどれだけが広告によるものかを
日ごとに見えるようにする。

各 ASIN 行の直下に広告行を1本足し、同じ日付列に広告経由の個数を書く。

## 決定事項

| 論点 | 決定 |
|---|---|
| 指標 | `unitsSoldSameSku14d`（広告をクリックした人がその広告商品自身を買った個数、14日アトリビューション） |
| 広告種別 | スポンサープロダクトのみ |
| 遡及更新 | 毎日、直近14日分を上書きする |
| 対象範囲 | 全 ASIN 行（「過去」「やめる」「様子見」の下も含む） |
| 広告行の印 | A列は空、H列（商品名）に「広告経由」 |
| 過去分 | 直近90日を一度だけバックフィルする |

### なぜ 14 日アトリビューションで、毎日上書きし直すのか

広告の成果は後から加算される。クリックの14日後までに発生した購入が、そのクリックの日付に
紐づけられる。したがって「昨日の広告経由の個数」は翌日時点では確定しておらず、
以降14日間かけて増えていく。

昨日分だけを1回書いて終わりにすると、すべての過去日が過小のまま固定される。
毎日、直近14日分を取り直して上書きすることで、値が確定値に収束する。

## シートの形

### 現状

- 4行目がヘッダー。A列が ASIN、H列が商品名
- 3行目が総売上、1行目と4行目に日付ラベル（シリアル値 + `dd` 書式）
- 日付列は「目標販売数」列（現在 CR）の右から**降順**に並ぶ。最新日を左に挿入していく
- ASIN 行は約74。間に「新商品」「様子見」「過去」「やめる」などの見出し行が混ざる
- 同じ ASIN が複数行に出ることがある（`B0FBSCPJJH`、`B0F5P3RM78`）

### 変更後

各 ASIN 行の直下に広告行を1本挿入する。74行 → 148行。

```
A列          H列(商品名)                09/02 09/01
B0HH5DR13D  スタンドルーペ 3.5倍 ...        3     5
            広告経由                      1     2
B0GQPRJNPF  A3壁掛け                       0     1
            広告経由                      0     0
```

- A列は空にする。「売上/今」へ `=ARRAYFORMULA('売上/日'!A4:A)` で流れる列であり、
  ここに文字列を置くと向こうの見た目が荒れる
- H列に「広告経由」と書く。行全体を薄いグレーで塗る
- 数式列（発注金額・原価・利益など）は広告行には入れない。空のままにする

### 広告行の見つけ方

**「A列が空 かつ H列が『広告経由』かつ 直前に ASIN 行がある」** 行を、その直前の ASIN 行に
紐づける。位置だけに頼らないので、間に空行が紛れ込んでも誤って書き込まない。

同じ ASIN が複数行にある場合、それぞれの行に広告行が付く。広告データは ASIN 単位でしか
取れないため、**同じ値を両方の広告行に書く**（売上個数の既存実装と同じ扱い）。

### 移行

`insert_ad_rows.py` を書き、一度だけ実行する。

- ASIN 行（A列が10文字）を下から順に走査し、直下に1行挿入して H列に「広告経由」を書き、背景を塗る
- 既に直下が広告行なら何もしない（何度実行しても増えない）
- `--dry-run` で挿入対象の行番号と件数だけを表示する

## データの取得

Amazon Ads API の非同期レポートを使う。

```
POST https://advertising-api-fe.amazon.com/reporting/reports
{
  "name": "ad-units-daily",
  "startDate": "2026-08-21", "endDate": "2026-09-03",
  "configuration": {
    "adProduct": "SPONSORED_PRODUCTS",
    "groupBy": ["advertiser"],
    "columns": ["date", "advertisedAsin", "unitsSoldSameSku14d"],
    "reportTypeId": "spAdvertisedProduct",
    "timeUnit": "DAILY",
    "format": "GZIP_JSON"
  }
}
```

作成 → `GET /reporting/reports/{reportId}` を `COMPLETED` になるまでポーリング →
`url` から GZIP_JSON を取得して展開する。`marketar/ad/tools/daily_report.py` の `AdsReports`
と同じ流れで、既に実績がある。

- 認証情報は **`data-engineer/dwld-ad-data/.env`** を読む
  （`AMAZON_CLIENT_ID` / `AMAZON_CLIENT_SECRET` / `AMAZON_REFRESH_TOKEN` / `AMAZON_PROFILE_ID` / `AMAZON_REGION`）。
  同じ資格情報を二重に持たないため、`marketar/ad` と同じくパス参照で借りる
- SP-API の認証とは別物。トークンの取得先も `https://api.amazon.com/auth/o2/token` で共通だが、
  scope が `advertising::campaign_management` で、`REFRESH_TOKEN` も別

戻り値は `dict[str, dict[str, int]]`（日付 `YYYY-MM-DD` → ASIN → 個数）にまとめる。
レポートに現れない ASIN・日付は**キーを作らない**。0 と欠測を混同しないため。

**レポートに行が無い ASIN の意味。** Ads レポートは1リクエストで全キャンペーンを横断して返すため、
取得そのものが成功していれば、その日の広告実績は行の有無に関わらず完全である。ある ASIN の行が
無いのは「取得できなかった」のではなく「その日、広告を出していなかった／クリックが無かった」ことを
意味し、これは正常な状態。実測（2026-09-01、`tools/check_ads_columns.py`）では、売上/日の広告行が
ある約74 ASIN のうち46 ASIN しかレポートに現れず、残り約28件は広告未出稿によるものとみられる。

この非対称性から、**0埋めの責務はリポジトリ側ではなくシート書き込み側（Task 4 の `AdSalesSheet`）に置く。**
`get_daily_units` はこれまでどおり現れなかった ASIN のキーを作らないが、書き込み側は
「その日の取得に成功していれば、レポートに現れなかった広告行にも 0 を書く」（詳細は後述の
「書き込みの手順」）。こうすることで、シート上で「広告未出稿（0）」と「取得失敗（空欄のまま）」を
区別できる。

### 取得できなかったときの扱い

レポートの作成・ポーリング・ダウンロードのいずれかが失敗したら、**何も書かずに異常終了する**。
部分的に書いて「広告経由が減った」ように見せない。launchd のラッパーが Slack へ通知する。

## 書き込み

### 既存の日次ジョブには入れない

`main.py daily`（毎日 1:00）は SP-API の `orderMetrics` を ASIN ごとに叩くため4分以上かかり、
「失敗が全 ASIN の10%を超えたら中断」する設計になっている。ここに Ads のレポート生成待ち
（数分のポーリング）を足すと、片方の失敗が両方を巻き込む。

`main.py ads` を新設し、**毎日 2:00**（売上ジョブの後）に別の launchd ジョブとして走らせる。

順序に意味がある。**日付列を作るのは売上ジョブの責務**であり、広告ジョブは既にある列に
書き足すだけにする。存在しない日付列は作らない（列の二重挿入を防ぐ）。

### 書き込みの手順

1. シートを読み、ASIN 行と広告行の対応（`dict[str, list[int]]`: ASIN → 広告行の行番号リスト）を作る
2. 直近14日分の広告データを1リクエストで取得する
3. 各日付について、日付列を4行目のシリアル値から探す。**無ければその日はスキップする**
4. 対象セルを `batch_update` 1回でまとめて書く（74行 × 最大14列）
5. 日付列の書式や1行目・4行目のラベルには触らない。総売上（3行目）にも触らない
6. **0埋めの規則。** 日付列が存在し、かつその日のレポート取得が成功している場合は、
   **広告行を持つ全 ASIN のセルに値を書く**（レポートに現れなかった ASIN は 0 を書く）。
   取得そのものが失敗した日は「取得できなかったときの扱い」のとおり1セルも書かない。
   空欄のまま残さないのは、シート上で「広告未出稿（0）」と「取得失敗（空欄）」を
   見分けられるようにするため

セルのノートは触らない。ノートは売上行の「その日の価格」に使われており、別の情報である。

## あわせて直す：「売上/今」の行ずれ

`RealtimeSalesSheet.write_realtime_sales` は、A列から10文字の値だけを抜き出してリストにし、
**2行目から詰めて**「個数」「売上」を書いている。

一方 A列は `=ARRAYFORMULA('売上/日'!A4:A)` で流れてくるため、見出し行（「新商品」「様子見」
「過去」など）も**行として存在する**。抜き出す側だけが見出し行を飛ばし、書き込む側は
詰めて書くので、**見出し行の数だけ値が上にずれている**。

広告行を74本挟むとこのずれは決定的になる。**A列の実際の行位置に書く**方式へ直す。

- `get_asin_list()` が ASIN と行番号の対応を保持する
- `write_realtime_sales` はその行番号へ書く。ASIN でない行（見出し行・広告行）は**空白で埋める**
- 書き込みは「個数」列・「売上」列それぞれ1レンジずつの `batch_update` にまとめる

これは既存バグの修正でもある。修正後は「個数」「売上」が正しい商品の行に並ぶ。

## 過去分のバックフィル

`backfill_ad_sales.py <開始日> <終了日>` を用意する。

- Amazon Ads のレポートは**1リクエストあたり最大31日**、データ保持は**過去95日程度**。
  90日を埋めるには31日ずつ3回に分ける
- 日次ジョブと同じ書き込み経路を通す。既にある日付列を探して上書きするだけなので、
  何度実行しても列は増えない
- 日付列が無い日はスキップし、スキップした日数を最後に出力する

## テスト

`py_tests/` に pytest で追加する。ワークシートはモックにする（既存のテストに倣う）。

- 広告行の解決：ASIN 行の直下が「広告経由」ならその行番号を返す／直下が別の ASIN 行なら含めない／
  同じ ASIN が2箇所にあれば広告行も2つ返す
- 日付列が無い日はスキップし、他の日は書かれる
- レポートに現れない ASIN のセルは**触らない**（0 を書かない）
- レポート取得の失敗時に1セルも書かずに例外を上げる
- ポーリングが `COMPLETED` になるまで繰り返し、GZIP_JSON を展開して行を返す
- `RealtimeSalesSheet`：見出し行・広告行を挟んでも、値が ASIN と同じ行に並ぶ

## 受け入れ基準

1. `insert_ad_rows.py --dry-run` が挿入対象74行を列挙し、本実行後にシートが148行になる。
   再実行しても行が増えない
2. `main.py ads` を手で走らせると、直近14日分の広告行に値が入る。売上行の値・ノート・
   総売上・日付ラベルが変化しない
3. `backfill_ad_sales.py` で90日分が埋まる
4. 「売上/今」の「個数」「売上」が、A列に表示されている商品名と同じ行に並ぶ
5. launchd の `com.automation.download-amazon-data-ads` が
   `launchctl print gui/$(id -u)/<label>` で `runs` を増やし、`last exit code = 0` になる
   （plist とラッパーは `~/Documents` の外に実ファイルで配る。`ops/sync_agents.py` に登録する）

## リスクと未検証事項

- **`groupBy: ["advertiser"]` + `unitsSoldSameSku14d` は実物で疎通確認済み（2026-09-03）。**
  `tools/check_ads_columns.py` で 2026-09-01 分を取得し、フォールバック無しで1回目のリクエストが通った。
  46 ASIN 分の行が返り、代表値は上位から `B0FR3CZRGP: 74`, `B0FKH5PGQ6: 67`, `B0F9WPDW92: 48`（いずれも同 ASIN の複数キャンペーン分を合算した値）
- Ads API のレポートは生成に数分かかる。`MAX_POLLS` を超えたらタイムアウトさせ、その日は書かない
- 行の挿入は「売上/今」の行数も同じだけ増やす。条件付き書式やグラフの範囲が
  意図せず広がっていないか、移行後に目視で確かめる
