# 「売上/日」シート仕様

**日付:** 2026-09-07
**目的:** このシートを Web アプリで置き換えるための仕様。**シートを見なくても再現できる**ことを目指す。

スプレッドシート `1Z3P0iL19r3gA9-NG8x2e_42pGhrEs_wFMLWLbFvReAw` のシート
`売上/日`（gid=551300985）。

---

## 1. 何のためのシートか

**商品（ASIN）× 日付**の板。1商品につき5行、1日につき1列。
「どの商品がどの日に、いくつ売れて、いくら残ったか」を一望する。

読む人がこの板に求めているのは3つ。

1. **今日いくら残っているか** — 行2（総売上）・行3（営業利益の合計）・行4（利益率）
2. **どの商品が稼いでいて、どれが赤字か** — 営業利益の行と色
3. **どの商品が在庫切れになりそうか** — 在庫日数の列と色

書き込みは launchd の定期実行が行う。人が手で入れるのは商品の追加・並べ替え・
備考・仕入先などの静的な情報だけ。

## 2. グリッド構造

### 2.1 予約行（行1〜5）

| 行 | 中身 | 書式 |
|---|---|---|
| 1 | 日付（シリアル値） | `dd`（日だけ表示）、10pt |
| 2 | **総売上**（円で保持し表示だけ千円） | `#,##0,`（千円・単位文字なし）、8pt |
| 3 | **営業利益の合計** = `SUMIF(商品名列, "営業利益", その列)` | `#,##0,`、8pt |
| 4 | **利益率** = `IF(行2=0,"",行3/行2)`。A列に見出し「利益率」 | `0%`、8pt |
| 5 | 日付（シリアル値）。**列を特定する正本** | `dd`、10pt |

- **行1と行4に同じ日付を書く。** 列の挿入時に両方書かないと、挿入だけ成功して
  落ちたときに列を再発見できず、同じ日付の列がもう1本入る
- 日付シリアルは Google Sheets の基準日 **1899-12-30** からの日数
- 日付列は**新しいものが左**。当日列が最左に作られる

### 2.2 商品ブロック（5行）

| # | ラベル（商品名列の値） | 中身 |
|---|---|---|
| 0 | （商品名そのもの） | その日の**売上個数**。セルのノートに**その日の価格** |
| 1 | `営業利益` | **数式** `=IF(粗利益セル="","",粗利益セル-N(広告費セル))` |
| 2 | `広告経由` | 広告経由の売上個数 |
| 3 | `粗利益` | 売上 −（販売手数料 + FBA手数料 + 原価）× 個数 |
| 4 | `広告費` | その日の広告費 |

- **ラベル行は「A列が空 かつ 商品名列がラベル名 かつ 直前に ASIN 行がある」で特定する。**
  位置だけに頼らない（空行や見出し行が紛れ込むため）
- ラベル行の高さは ASIN 行の**半分**（39px → 19px）。A列〜商品名列だけ薄いグレー
- **`広告経由` `粗利益` `広告費` は行グループで折りたたむ。** たたんだ状態でも
  ASIN 行と営業利益が並んで見えるよう、営業利益を先頭に置いている
- 商品の間に**見出し行**（A列に `様子見` `新商品` などの短い文字列）が入る。
  ASIN は10文字なので、長さで区別する

### 2.3 同じ ASIN が複数行にある

同一商品を2回登録している行が実在する（`B0FBSCPJJH` `B0F5P3RM78`）。

- ASIN → 行番号は**リスト**で持つ。`dict[str, int]` にすると片方が毎日空になる
- 個数・価格・粗利益は**重複した全行に**書く
- **総売上はユニーク ASIN で合算する**（重複分の二重計上を防ぐ）
- SKU は行ごとに違うことがあるため、**SKU → ASIN の向きで持つ**

## 3. 列カタログ

### 3.1 列の特定方法

**行4のヘッダーで列を引いてはいけない。** `Column 133` のような自動採番が混ざっている。
**行1の英語キー**が正本。キーが無い列は行4のヘッダー名で引くが、その場合は
**改行を除去し大小文字を畳んで**比較する（`FBA\n在庫日数`、`SKU` と `fnsku` が混在）。

## 4. データの出どころ

| 何を | どこから | いつ | 実装 |
|---|---|---|---|
| 売上個数・総売上 | SP-API `sales/v1/orderMetrics`（ASIN ごと1リクエスト） | 前日分 1:00 / 当日分 毎時0分 | `main.py daily` / `today` |
| 価格（セルのノート） | SP-API 競合価格 | 1:00 | `main.py daily` |
| 広告経由の個数・広告費 | Amazon Ads `spAdvertisedProduct` レポート（DAILY） | 2:00、直近14日を毎日上書き | `main.py ads` |
| 粗利益（見積） | 売上 − シートの手数料・原価 | 1:00 と毎時 | `main.py daily` / `today` |
| 粗利益（実測） | SP-API `finances/v0/financialEvents` + 注文レポート | 3:00、直近30日 | `main.py finances` |
| 在庫数・SKU | 「マネジメント」シート（別ジョブが更新） | — | 数式 |

### 4.1 欠測とゼロを混同しない

- **取得に失敗した ASIN はセルを空のままにする。** 0 を書くと「売れなかった」と
  区別できない
- **広告レポートに現れなかった ASIN には 0 を書く。** 空にすると「広告未出稿」か
  「取得失敗」か分からない
- **レポートが `COMPLETED` かつ0行なら書き込まない。** 設定ミスで全ASIN・全日付が
  0 になり、翌日以降も自己修復しない
- **原価が欠けた ASIN は粗利益を空にする。** 書かずに飛ばすと前回の見積が残り、
  最新の数字に見える

### 4.2 実測は約7日遅れる

`financialEvents` は**精算期間（settlement）単位で確定する**。2026-09-06 に取得したとき、
8/30 以降の実測は丸ごと0だった。さらに注文日から数日遅れて出荷される分の手数料は
次の精算に入るため、古い日でも 100% には届かない。

| 8/23 | 8/27 | 8/28 | 8/29 | 8/30以降 |
|---|---|---|---|---|
| 99% | 91% | 71% | 22% | 0% |

**窓は30日**。14日だと確定する前に対象から外れ、永久に埋まらない。

### 4.3 粗利益の計算

```
粗利益 = 売上 − 実測手数料 − 返金された売上
        − (販売手数料 + FBA手数料) × 未出荷個数     ← 見積
        − 原価 × 販売個数

未出荷個数 = clamp(orderMetrics の個数 − 出荷済み個数, 0, 販売個数)
```

- **売上は orderMetrics に統一する。** Finances の `Principal` と orderMetrics の
  `totalSales` は税の扱いが違う。実測に置き換えるのは**手数料の項だけ**
- 未出荷分は見積のまま。実測だけで引くと手数料が過小になり利益が過大に出る
- 原価は実測できない。返品された分の原価も戻さない
- **黄色 = まだ動く / 白 = 確定。** その日その商品の全個数に実測が付いたときだけ白。
  売れた日に実測が1件も無いのを白にしてはいけない

## 5. 色の意味

| 対象 | 条件 | 見た目 | スケール |
|---|---|---|---|
| 売上個数・広告経由 | — | うすい赤 → うすい青 | **商品ごと** |
| 順位 | — | うすい青（最上位） → うすい赤（最下位） | **商品ごと** |
| 順位 | — | うすい青（最上位） → うすい赤（最下位） | **商品ごと** |
| 順位 | — | うすい青（最上位） → うすい赤（最下位） | **商品ごと** |
| 営業利益 | **< 0** | 濃い赤 + 白太字 | — |
| 営業利益 | 0円 | 白 | **商品ごと** |
| 営業利益 | > 0 | 徐々に青。**その商品の最大益で最も濃い** | 同上 |
| 粗利益 | 見積 | うすい黄 | — |
| 粗利益 | 確定 | 白 | — |
| 利益率（`PROFIT_RATE`） | — | 濃い赤 ← 0% = 白 → 濃い青 | 列全体 |
| FBA在庫日数 | **≤ 14** | 濃い赤 + 白太字 | — |
| 在庫日数 / 目標売上在庫日数 | ≤ 72 | うすい赤 | — |
| 価格（ASIN行のノート） | 前日より安い | **赤字・太字**（背景ではない） | — |
| 価格（同上） | 前日より高い | **青字・太字**（背景ではない） | — |

**悪い = 赤、良い = 青**でそろえ、行の種類は**色味の濃さ**で見分ける
（個数はうすい、営業利益は濃い）。

**個数も営業利益も商品ごとのスケール**にする理由: 日次200個の商品と数個の商品を同じ物差しに
載せると、後者がすべて同じ色になって読めない。営業利益は 0 を白に固定してあるので
統一スケールでも意味が保てる。

**営業利益の青は1000円から1万円まで。** 0 から振ると数百円の差で全体がうっすら青くなる。
上限を `MAX` にすると外れ値に引っ張られる（1000円超599セルの中央値 2,811円 に対し
最大 49,580円 で、中央値が 3.7% の位置になりほぼ白に潰れた）。**上下とも固定値にする。**

**営業利益の 0 は目立たせない。** 実データで 0 以下は 38% あり、うち 93% が
ちょうど 0（売れなかった日）。赤くしても打つ手が無い。

## 6. セルのノートが持つ情報

**ノートはただの注釈ではなく、データを持っている。** Web アプリでは別フィールドにする。

| 場所 | 中身 | 用途 |
|---|---|---|
| ASIN 行 × 日付列 | その日の価格（`379.0`） | 前日比の色分け。**セルの値ではなくノートを読む** |
| 粗利益 行 × 日付列 | `見積 3,900 / 実測 3,750` | 上書き前の見積の履歴 |
| 行2 ×「目標販売数」列 | `HH:MM`（**セルの値**。ノートではない） | 当日列がいつ時点の数字か |

## 7. 派生シート

| シート | 中身 |
|---|---|
| `売上/今` | 当日のリアルタイム売上。ASIN ごと1行。`売上/日` から自社価格を引く |
| `手数料乖離` | 直近30日の見積 vs 実測。**FBA手数料と販売手数料を分けて**出す |
| `マネジメント` | 納品プラン。在庫数・SKU の供給元 |
| `仕入情報` | 仕入先・購入価格 |

### 7.1 手数料乖離シート

| 列 | 中身 |
|---|---|
| ASIN | `=HYPERLINK("https://www.amazon.co.jp/dp/…", ASIN)` |
| 商品名 / 個数 | 出荷済み個数（返金は差し引く） |
| 見積 販売手数料/個 / 実測 / 差 | 販売手数料は**価格に比例**。セール中に下がるのは当然 |
| 見積 FBA/個 / 実測 / 差 | FBA手数料は**価格に連動しない**。差が出ていれば列が古い |
| 合計 差/個 / 更新 | |

分けないと原因が読めない。実例（`B0F37S31GY`、95個）は実測 FBA 252円/個・
`Commission` 37.2円/個・`ShippingChargeback` 6.9円/個 に対し、シートは
FBA 318円・販売手数料 189円。見積の189円は「1,149円 × 15% × 1.1」だが、
実測の37円は「667円 × 5%」に一致する（低価格帯の手数料率）。

## 8. Web アプリで置き換えるときの要点

### 8.1 データモデル

シートの二次元グリッドは、実質**3つのテーブル**でできている。

```
product      (asin, name, sku[], price, cost, referral_fee, fba_fee,
              dimensions, supplier[], note, target_units, delivery_class, …)
daily_metric (asin, date, units, price, ad_units, ad_cost,
              gross_profit, gross_profit_estimate, settled)
fee_gap      (asin, window_start, window_end, quantity,
              estimated_referral, actual_referral, estimated_fba, actual_fba)
```

- `営業利益` は保持せず `gross_profit - ad_cost` で導出する
- `settled` を持てば「黄色 / 白」の出し分けができる
- 重複 ASIN はシート固有の事故。**Web アプリでは product を一意にする**

### 8.2 シートに引きずられている制約（引き継がなくてよい）

- 行1と行4の二重の日付ラベル
- ラベル行を商品名の文字列で判定していること
- 予約行（行1〜4）を避けるガード
- 列を「行1の英語キー」で引いていること
- 千円単位を数値書式で表現していること（値は円で保持している）
- `#REF!` を含む壊れた数式列

### 8.3 引き継ぐべき仕様

- **欠測とゼロを区別する**（4.1）
- **実測は約7日遅れる。窓は30日**（4.2）
- **未出荷分は見積のまま**（4.3）
- **色の意味**（5）
- **価格の履歴**（現在はノート）
- 手数料の**FBAと販売手数料を分けた乖離表**（7.1）

### 8.4 外部 API の制約

| API | 制約 |
|---|---|
| `sales/v1/orderMetrics` | ASIN ごと1リクエスト。77件で数分。`interval` は **UTC の `Z` 形式**（`+09:00` だと何も返らない）。`granularityTimeZone=Asia/Tokyo` |
| `orders/v0/orders` | **1分あたり1リクエスト**（バースト20）。数百ページは不可能 |
| Reports API `GET_FLAT_FILE_ALL_ORDERS_DATA_BY_ORDER_DATE_GENERAL` | 注文日の取得はこちら。1日1,372行を約20秒。**cp932**。`purchase-date` は `+09:00` |
| `finances/v0/financialEvents` | `PostedBefore` は**2分前より新しいと 400**。`NextToken` は他のパラメータと**排他** |
| Amazon Ads `spAdvertisedProduct` | 成果はクリックから14日後まで加算される。直近14日を毎日上書きする必要がある |

### 8.5 返金イベントの形（実物で確認済み）

| | 出荷 | 返金 |
|---|---|---|
| リスト | `ShipmentEventList` | `RefundEventList` |
| 明細 | `ShipmentItemList` | `ShipmentItemAdjustmentList` |
| 手数料 | `ItemFeeList`（負） | `ItemFeeAdjustmentList`（戻しは正・返金手数料は負が混在） |
| 売上 | `ItemChargeList` の `Principal` | `ItemChargeAdjustmentList` の `Principal`（負） |
| 個数 | `QuantityShipped` | `QuantityShipped` — **返金でも正の値**。符号は自分で反転する |

2026-08-20〜08-27 の実績で出荷 5,156件・返金 41件（0.8%）。

## 10. 過去にやらかしたこと

Web アプリでも同じ形の失敗が起こりうるので残す。

- **条件付き書式を全件削除した。** 「自分の規則を入れ直す」つもりで既存の規則まで
  消し、下地の直接指定が露出した（S〜X列）。**自分が入れたものだけを消すこと**
- **「広告経由の1つ上が ASIN 行」と決め打った。** ラベルを並べ替えたときに別の行を
  掴み、**72件の ASIN 行を 10px に潰した**。ブロックの起点は**先頭ラベル**から取る
- **新商品の行挿入が2行のままだった。** 定義を増やしても挿入側を直さず、新商品だけ
  永久に空欄になった。**行数とラベルの定義は1箇所に持つ**
