# 「売上/日」に当日の粗利益と広告費を並べる

2026-09-05

## 目的

「売上/日」は各 ASIN が2行（売上個数・広告経由の売上個数）になっている。ここに
**粗利益**と**広告費**の行を足し、その日その商品が「いくら売れて、いくら広告に使い、いくら残ったか」を
1画面で見えるようにする。

## 決定事項

| 論点 | 決定 |
|---|---|
| 行の並び | 売上個数 / 広告経由 / 粗利益 / 広告費 |
| 粗利益の定義 | 実売上 − 販売手数料 − FBA手数料 − 原価 |
| 手数料 | **当日は見積、後から実測で上書き**する |
| 実測の取り直し | 直近 **14日** |
| 実測をどの日の列に入れるか | **売れた日（注文日）**の列 |
| 見積と実測の区別 | **背景色**（見積は薄い黄色、実測で塗りを外す） |
| 実測の取得方法 | Orders API と Finances API を注文IDで突き合わせる |

### なぜ注文日の列に入れるのか

Finances API のイベントは「いつ決済されたか」で並ぶ。9/1に売れた商品の手数料が9/3に確定する、という
ずれが常に起きる。決済日の列に入れると、**同じ列の売上と手数料が別の取引のものになり**、
引き算が成立しない。粗利益を意味のある数にするには、注文日へ寄せる必要がある。

## シートの形

各 ASIN が4行になる。行の識別は既存の広告行と同じで、**A列は空、商品名列にラベル**を置く。

```
A列          H列(商品名)              09/05  09/04
B0HH5DR13D  スタンドルーペ 3.5倍 ...     3      5
            広告経由                    1      2
            粗利益                  1,240  2,100
            広告費                    180    240
```

77 ASIN × 4行 + 見出し行 ≈ **320行**になる（現在は約166行）。

- 予約行（1〜4行）への誤書き込みは既存のガード（`row > HEADER_ROW`）がそのまま効く
- 数式列（発注金額・原価・利益など）は新しい2行には入れない。空のままにする
- 行の紐づけは既存の `AdSalesSheet._bind_ad_rows` と同じ考え方で、
  「A列が空 かつ 商品名列が該当ラベル かつ 直前に ASIN 行がある」で解決する

行ラベルは商品名列に入れる文字列そのもので、**この4つが行の識別子**になる。

| 行 | ラベル | 備考 |
|---|---|---|
| 1本目 | （ASIN 行。商品名が入る） | A列に ASIN |
| 2本目 | `広告経由` | 既存 |
| 3本目 | `粗利益` | 新規 |
| 4本目 | `広告費` | 新規 |

広告行と同じく、A列は空、行の背景は薄いグレー（`{red: 0.95, green: 0.95, blue: 0.95}`、
A列から商品名列まで）で揃える。

## 計算

### 粗利益（見積）

```
実売上 − (販売手数料 + FBA手数料 + 原価) × 個数
```

- **実売上**は SP-API の `orderMetrics` が返す金額（`SalesInfo.total_sales_amount`）。既に取得済みで、
  セール価格が反映される。個数 × 自社価格ではない
- **販売手数料 (BR) / FBA手数料 (BS) / 原価 (BQ)** はシートの既存列から読む。**いずれも1個あたり**
  （BQ は `=BF+BE+BD+AS`、BV の利益は `=M−BU−BQ` で自社価格から引いている）

### 粗利益（実測）

```
実売上 − 実測手数料 − 原価 × 個数
```

実測手数料は Finances API の `ItemFeeList`（`Commission`、`FBAPerUnitFulfillmentFee` 等）の合計。
原価は実測の対象外なので見積と同じ BQ を使う。

### 広告費

Amazon Ads の `spAdvertisedProduct` レポートに **`cost` 列を足す**だけ。日付 × ASIN で既に
`unitsSoldSameSku14d` を取っているので、同じ1リクエストで両方取れる。

## 実測手数料の取り方

Finances API のイベントは注文IDと SellerSKU を持つが、**注文日も ASIN も持たない**。
2つの対応表を作って結合する。

```
Finances events → (注文ID, SellerSKU, 手数料)
Orders API      → (注文ID, 注文日)
売上/日 の SKU列 → (SellerSKU → ASIN)
                ↓
        (注文日, ASIN) → 手数料
```

### Orders API は注文一覧だけを使う

既存の `OrdersRepository.get_orders_with_items` は**使わない**。`_build_order` が注文1件ごとに
`getOrderItems` を呼び、3秒スリープを挟む作りなので、1万件で8時間以上かかる。

必要なのは `注文ID → PurchaseDate` だけなので、**注文一覧のエンドポイントだけを使う**
（100件/ページ、2秒スリープ）。1万件で約200秒。`Order` エンティティに `purchase_date` を足す。

### ASIN の特定はシートの SKU 列で行う

商品明細を取らずに済ませるため、Finances の `SellerSKU` を「売上/日」の SKU 列（現在 AH）で
ASIN に引き当てる。

**この列は「マネジメント」シートへの xlookup で、`#N/A` になっている行がある。** 出品レポートに
新 ASIN が載るまで解決しないため（`classify-delivery` が `有効なSKUが解決できません` で落ちるのと同じ原因）。
**SKU が引けない ASIN は実測手数料を紐づけられず、見積のまま残る。** これは正常な状態として扱う。

## 見積と実測の区別

粗利益の行のセルに背景色を付ける。

| 状態 | 背景 |
|---|---|
| 見積 | 薄い黄色 `{red: 1.0, green: 0.95, blue: 0.8}` |
| 実測で確定 | 塗りを外す（`repeatCell` + `fields: userEnteredFormat.backgroundColor`） |

塗りを外すときは、`SalesSheet._clear_backgrounds` と同じやり方を使う。`format` は
`userEnteredFormat` にマージするだけで色を消せないため。

売上行の価格変動（値下げ=赤 / 値上げ=水色）とは別の行なので衝突しない。ただし
**行全体ではなくその日付列のセルだけ**を塗る。行全体を塗ると、まだ実測が来ていない他の日の
セルまで確定済みに見えてしまう。

## どのジョブが何を書くか

| ジョブ | 書くもの | 実行 |
|---|---|---|
| `main.py today` | 売上個数、**粗利益（見積）** | 毎時0分（既存） |
| `main.py daily` | 売上個数、価格、**粗利益（見積）** | 毎日 1:00（既存） |
| `main.py ads` | 広告経由、**広告費** | 毎日 2:00（既存） |
| **`main.py finances`（新規）** | **粗利益（実測で上書き）** | 毎日 3:00 |

粗利益（見積）は売上と同じジョブが書く。実売上と個数がその場にあるため、追加の API 呼び出しが要らない。

`finances` を 3:00 に置くのは、日付列を作るのが `daily`（1:00）の責務であり、**既にある列に
書き足すだけにする**ため。`ads`（2:00）と同じ考え方。

## 取得できなかったときの扱い

- **手数料や原価が空の商品は、粗利益のセルを空にする。** 新商品は BR/BS/BQ が未設定のことがあり、
  0 として扱うと**利益が過大に見える**。数字を出さない方が安全
- **返金は14日の窓に入るものだけ反映する。** 20日前の注文への返金は注文日が窓の外なので落ちる。
  実測が最終確定値にならないケースが残る
- レポートやAPIの取得に失敗したら、**何も書かずに異常終了する**（既存の `ads` と同じ）
- `finances` にも締切を設ける。10分前後を見込むが、実測してから値を決める

## 移行

既存の `insert_ad_rows.py` を「各 ASIN に必要なラベル行を順番どおりに揃える」形へ一般化する。
既に広告行を持つ77 ASIN には、**粗利益行と広告費行を2本ずつ追加**する。

- 既にある行は動かさない（広告経由の行に入っている実データを保つ）
- 何度実行しても増えない（既存の冪等性と復旧ロジックを引き継ぐ）
- `--dry-run` で対象を確認できる

新商品を足すときは `marketar/listing-creator/write_sales_sheet.py` が**4行挿入**するよう直す
（現在は2行）。

| 対象 | 影響 | 対応 |

| `AdSalesSheet` | 広告費の行も書くようになる | 拡張 |

## テスト

`py_tests/` に pytest で追加する。ワークシートと HTTP セッションはモックにする。

- 粗利益（見積）の計算：実売上・個数・BR/BS/BQ から期待値が出る
- BR/BS/BQ のいずれかが空なら粗利益のセルを空にする（0 を書かない）
- 実測手数料が注文日の列に入る（決済日ではない）
- SKU が `#N/A` の ASIN は実測の対象から外れ、見積のまま残る
- 実測で上書きしたセルの背景色が外れる
- 広告費が広告費の行に入り、広告経由の行を壊さない
- 14日の窓の外の注文に対する返金が混ざらない
- 移行スクリプトが既存の広告行を動かさず、2行だけ足す。再実行しても増えない

## 受け入れ基準

1. 移行後、各 ASIN が4行になり、既存の売上個数と広告経由の値が変わっていない
2. `main.py today` を走らせると粗利益（見積）が入り、薄い黄色になる
3. `main.py ads` を走らせると広告費が入る
4. `main.py finances` を走らせると直近14日の粗利益が実測で上書きされ、塗りが外れる
5. 実測の粗利益が、同じ日の売上・広告費と突き合わせて説明できる値になっている
6. launchd の `com.automation.download-amazon-data-finances` が
   `runs` を増やし `last exit code = 0` になる。**登録した翌日にもう一度 `runs` を確認する**

## リスクと未検証事項

**2026-09-05、`tools/check_finances_api.py` で疎通確認済み。** 以下は実測した事実。

- **Finances API はこの資格情報で呼べる。** `GET /finances/v0/financialEvents` は403にならず、
  直近7日・10ページ（キャップ）で `ShipmentEventList` 991件・`ShipmentItemList` 1077件を取得できた。
  `ShipmentItemList[]` は全件 `SellerSKU` を持つ。`ItemFeeList[].FeeType` は実際に
  `FBAPerUnitFulfillmentFee`（1077件、例 -222円）・`Commission`（1000件、例 -110円/-85円/-35円）・
  `FixedClosingFee` / `GiftwrapChargeback` / `ShippingChargeback` / `VariableClosingFee`
  （いずれも1000件、金額は0円が大半）が来た。**手数料はマイナスの値で返る**（差し引くのではなく
  加算すればよい）
- **注文件数は見積の約1.8倍だった。** `GET /orders/v0/orders` を1日分（2026-09-03・JST基準でUTC日境界）
  叩いたところ **1,240件・13ページ**（100件/ページ、`NextToken` 走査）。取得に**31.0秒**かかった
  （`SpApiAuthenticator.request` が1呼び出しごとに最低2秒スリープするため）。1日1,240件のペースなら
  14日で概算 **17,360件**（見積の1万件より多い）。実測ペース（0.025秒/件、注文明細は叩かない前提）で
  試算すると14日分の取得は**7〜8分程度**（1日あたり13ページ×14日=182ページ、182ページ×約2.4秒/ページ
  ≈ 7.3分）。想定より件数は増えるが、実行時間としては launchd の1ジョブに収まる範囲
- **SKU 列の `#N/A` は「売上/日」全体で36件（総SKUセル93件中）だが、これには商品行以外が混ざる。**
  内訳は ASIN(10桁英数字)を持つ実商品行が75件中18件（24%）、残りはメモ行（「様子見」「やめる」等、
  6件）と数式が伸びた末尾の空行（12件）。**実測手数料を紐づけられないのは実商品行の18/75（24%）。**
  例: [B0FBSCPJJH](https://www.amazon.co.jp/dp/B0FBSCPJJH)、
  [B0DX7132XX](https://www.amazon.co.jp/dp/B0DX7132XX)、
  [B0DK1G2WB1](https://www.amazon.co.jp/dp/B0DK1G2WB1)。この24%は実装後も見積のまま残る前提で進める
- `finances` の締切値は実測してから決める。健全な実行を切る締切は無いより悪い（14日分の実行時間が
  7〜8分程度と分かったため、締切は余裕を見て15〜20分程度を軸に検討する）
