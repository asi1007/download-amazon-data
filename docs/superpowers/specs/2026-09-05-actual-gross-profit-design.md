# 粗利益を実測手数料で上書きし、見積との差を抽出する

**日付:** 2026-09-05
**対象:** `data-engineer/download-amazon-data`
**前提となる仕様:** `2026-09-05-gross-profit-and-ad-cost-design.md`（見積の粗利益・広告費）

## なぜ作るか

見積の手数料は**特定の商品で大きく外れる**。2026-08-20〜08-27 の実測（51商品・5,904個）で確認した。

| | 金額 |
|---|---|
| 見積の手数料合計 | 1,715,273円 |
| 実測の手数料合計 | 1,774,367円 |
| 差 | **+59,094円（+3.4%）** |

実測のほうが高く、**粗利益は過大に出ている**。ただし問題は合計ではなく商品ごとのばらつきで、
シートは ASIN × 日で見るものだからこちらがそのまま出る。

| ASIN | 個数 | 見積/個 | 実測/個 | 差 |
|---|---:|---:|---:|---:|
| B0GSLDK2DJ | 114 | 259円 | 396円 | **+53%** |
| B0HD5T1XF1 | 8 | 457円 | 292円 | **−36%** |
| B0FCHC2GVB | 12 | 436円 | 289円 | **−34%** |
| B0DT1DTYF6 | 87 | 255円 | 305円 | **+20%** |

51商品のうち **5%以上ずれているのが17商品、10%以上が8商品**。3商品は誤差ゼロだった。
「全体が数%ずれる」のではなく、**個々の商品で見積が古くなっている**（サイズ区分の変更などで
シートの FBA手数料が実態と合っていない）。

したがって本仕様の目的は2つある。

1. 粗利益を実測で上書きし、正しい数字にする
2. **見積と実測の差を抽出し、シートの手数料列のどれが古いかを分かるようにする**

2 が無いと、毎日上書きしているだけで**見積は永久に古いまま**になる。

## 何を作るか

`main.py finances` を追加し、`com.automation.download-amazon-data-finances` で毎日 3:00 に実行する。

### 対象期間

**直近14日**（注文日ベース、JST）。広告ジョブと同じローリング窓。
返金や手数料の後追い調整が14日を過ぎてから来た分は反映されない。

### 未出荷分は見積のまま

粗利益の3項は数える母集団が違う。売上は**注文**ベース、実測手数料は**出荷**ベース。
未出荷の注文には手数料イベントが無いので、実測だけで引くと手数料が過小になり
**利益が過大に出る** — しかも「確定した数字」に見えるタイミングで。

そこで（日付 × ASIN）ごとに個数を2つに分けて足し合わせる。

```
粗利益 = 実測分 + 見積分

実測分 = Σ(実売上 − 実測手数料) − 原価 × 出荷済み個数
見積分 = (売上合計 − 実売上合計) − (販売手数料 + FBA手数料 + 原価) × 未出荷個数

未出荷個数 = orderMetrics の個数 − 出荷済み個数
```

- **実売上は `financialEvents` の `Principal`** を使う。出荷済み分については売上も実測になる
- 未出荷個数が負になったら 0 に丸める（注文と出荷の期ずれで起こりうる）
- 原価はシートの `原価` 列。実測は取れないので出荷済み・未出荷とも同じ値を使う

### 黄色は「まだ動く」を表す

現状は書き込んだ全セルが黄色で、外す仕組みが無いため**永久に黄色**になっている。意味が無い。

- **未出荷個数が 0 の（日付 × ASIN）だけ黄色を外す。** 白 = その日その商品は確定
- 1個でも未出荷が残る日は黄色のまま
- 黄色を外すのは `repeatCell` + `fields: userEnteredFormat.backgroundColor`。
  `#,##0.0,"K"` の数値書式は残す（`format` は `userEnteredFormat` にマージするだけで消せない）

### 差の抽出

**(a) 「手数料乖離」シート** — 毎回上書き。直近14日の集計を `|差%|` の降順で並べる。
シートのどの手数料列を直すべきかが一目で分かることが目的。

| 列 | 内容 |
|---|---|
| ASIN | `=HYPERLINK("https://www.amazon.co.jp/dp/…", ASIN)` |
| 商品名 | 売上/日 から引く |
| 個数 | 出荷済み個数（実測が付いた分） |
| 見積/個 | 販売手数料 + FBA手数料 |
| 実測/個 | 実測手数料 ÷ 出荷済み個数 |
| 差/個 | 実測 − 見積 |
| 差% | 差 ÷ 見積 |
| 更新 | 実行時刻（JST） |

**(b) 粗利益セルのノート** — 上書きする前の見積を残す（`見積 1234 / 実測 1180`）。
乖離シートは最新14日しか持たないため、日ごとの履歴はここに残る。
価格を ASIN 行のノートに入れている既存の慣習と同じ形。

### SKU → ASIN

`financialEvents` は `SellerSKU` を返すので、売上/日 の `sku` 列で ASIN に引き直す。
シートに無い SKU は集計から外し、**外した件数を標準出力に出す**（黙って落とさない）。

### 返金

`RefundEventList` も同じ窓で取り、手数料の戻しと売上の戻しを差し引く。
`ShipmentEventList` だけを見ると、返品された注文で利益が過大になる。

## 設計上の判断

### 実測が取れなくても落とさない、ただし黙らない

Finances のロールが外れている・レポートが空、といった場合に見積を壊してはいけない。

- 実測が1件も取れなかった → **シートに触らず例外**（`EmptyFinancesResultError`）。
  黙って0件で正常終了すると launchd の失敗通知が鳴らない
- 一部の ASIN だけ実測が無い → その ASIN は見積のまま。件数を標準出力へ

### 日次ジョブとは別ジョブにする

`daily`（1:00）と `ads`（2:00）と同じ理由。getOrders は14日で 180ページ前後になり
7〜8分かかる。日次売上の SP-API 取得（4分）と混ぜると片方の失敗が両方を巻き込む。

### 冪等

同じ日に何度実行しても結果は同じ。列は作らない（作るのは `daily` の責務）。
日付列が無い日はスキップし、スキップした日数を出力する（`ads` と同じ契約）。

## テスト

- 未出荷が混ざる（日付 × ASIN）で、実測分と見積分が足し合わされること
- 未出荷個数が 0 のときだけ黄色が外れること
- 未出荷個数が負になる入力で 0 に丸められること
- 返金があると手数料と売上の両方が戻ること
- 実測が0件のとき例外を投げ、シートに触らないこと
- シートに無い SKU が集計から外れ、件数が返ること
- `batch_update` が `range` を書き換えても、書式・ノートの対象範囲が汚染されないこと
  （既存の `write_gross_profit` / `write_ad_metrics` と同じ罠）

## やらないこと

- 14日より前の遡及。返金や調整が後から来ても反映しない
- 原価の実測化。原価はシートの値のまま（仕入値は SP-API から取れない）
- 見積そのものの自動更新。**乖離シートを見て人が直す**。自動で書き換えると
  どの商品の見積が壊れているのかが分からなくなる
